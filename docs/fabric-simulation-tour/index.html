0.1 · Overview

A cloth solver that never leaves the GPU

BorrowedTorch.FabricSimulator is a MonoGame package. A compute shader integrates the particles, relaxes the threads between them and computes the normals. Then it stops. Your own vertex shader reads the same buffer and draws the sheet.

  • Verlet integration on a fixed 120 Hz step, Jacobi relaxation
  • Structural, shear and plastic bending threads, long-range pin attachments
  • Sphere and ground colliders, self-collision through a spatial hash
  • Live cuts and tears, wind as an air velocity
  • A rest deadband and a hold, so settled cloth, even a crumpled pile, stays exactly still
The sheet on the right is a small JavaScript port of the same rules: 36 × 26 points, the solver's thread function, its drag formula and its pin attachments. Drag across it to cut.

0.3 · Overview

Three classes and one boundary

  • FabricSettings is a plain object of knobs. It is checked and uploaded every frame, so changes apply live; the sheet fields (the grid, RestLength, SeedRipple) wait for Rebuild(), which AutoRebuild calls for you.
  • Fabric is the CPU model of the grid: placement, pins, pin distances, tears, triangle indices.
  • FabricEffect owns its own copy of the solver effect, the GPU buffers, the fixed-step clock and the dispatches.

The dashed boxes are GPU work. Nothing returns to the CPU in a normal frame. Cuts and pin changes re-measure the anchors on the CPU and upload them; only picking (CaptureSurface) and the diagnostics read back.

0.5 · Overview

                
The fixed-step clock

                
The solver always steps at SolverFrequencyHz (120 by default), whatever the frame rate.
                    Update adds the frame time to an accumulator and runs whole steps while it can.

                
    
                    
  • At 60 fps every frame runs exactly two steps.
    • 
                    
  • At 144 fps some frames run none and redraw the same pose. That is what InterpolationFraction
                        fixes (slide 1.5).
                    
    • 
                    
  • A slow frame catches up at most MaxStepsPerFrame steps; the rest of the backlog is
                        dropped (IsSaturated), so one hitch cannot snowball.
                    
    •

1.1 · Data model

                
One particle, sixty-four bytes

                
Every grid point is one FabricParticle. It is declared twice, in C# and in HLSL, field
                    for field. Every pass streams the whole grid, so anything derivable is left out: no velocity, no
                    texture coordinates.

                
The three pin fields are a copy. The solver keeps its pins in an 8-byte anchor buffer of its own
                    (slide 2.4) and writes them into the record every step, so a readback shows the pins in force as of
                    the last step, and an upload's values set them.

1.2 · Data model

                
Why there is no velocity field

                
Verlet integration keeps two positions instead of a position and a velocity. Velocity is simply the
                    gap between them, so anything that moves Position (a constraint, a collision) changes
                    the velocity too, for free.

                
next = Position + (1 − Damping) · (Position − PrevPosition) + a · dt²
PrevPosition
                    ← Position · Position ← next
                

                
The gap was measured over the last step, so when SolverFrequencyHz changes the solver
                    scales it by DisplacementScale (this step's length over the last one's), and Damping
                    is stated per 1/120 s and rescaled to the step (slide 4.7).

                
The hollow dot is PrevPosition, the filled one Position; the arrow is the
                    implied velocity.

1.3 · Data model

                
Three guards against drift

                
Because the HLSL is copied into the host's tree, the headers and the assembly can come from different
                    releases. Nothing in the toolchain checks that the C# and HLSL agree, so the library checks three
                    ways.

                
    
                    
  • Passes: the constructor looks up the technique and all eight passes by name. A solver
                        compiled from an older release lacks BendPass and GatherCandidatesPass,
                        and throws naming the pass, not on the first dispatch.
                    
    • 
                    
  • Size: Marshal.SizeOf must be 64. Catches a field added or resized.
    • 
                    
  • Defines: the constructor regex-reads #define FabricShaderContractVersion
                        (now 3) from the header on disk, and GroupSize and
                        ContactCandidateCapacity (32) beside it. Catches a reorder, which keeps the size at
                        64.

1.4 · Data model

                
Grid convention

                
The buffer is row-major: index = row × width + column. Row 0 is the free edge of
                    a hanging sheet, so the top row is height − 1 and V is flipped to put row 0 at the
                    bottom of the texture.

                
Texture coordinates come from the index alone, so rotating or reorienting the sheet never changes
                    them. Click a point.

1.5 · Data model

                
The renderer's view of the buffer

                
FabricParticleBuffer.fxh is what your draw shader includes. Binding FabricParticles
                    read-only is the correct, intended use.

                
D3D11 cannot bind one buffer for reading and writing at the same time; it silently
                    nulls one of the bindings. The last constraint round writes the buffer that becomes ParticleBuffer,
                    but your MonoGame fork unbinds every compute UAV right after each dispatch, so at draw time nothing
                    holds it for writing (slide 3.3). What breaks: declaring RWStructuredBuffer in a vertex
                    shader (the fork throws) or caching the buffer across frames.
                

                
FabricEvaluateVertex(vertexId, …) takes two kinds of id:

                
    
                    
  • below ParticleCount: a particle, interpolated between the last two steps
    • 
                    
  • at or above it: a seam vertex of a cut mesh, a weighted blend of three particles, or on a
                        strip one particle wide, of two plus an offset across them (chapter 5)
                    
    • 
                

                
Pins always draw at Position, so a pin the host moves between steps moves
                    at once. The solver also sets a pin's PrevPosition to its Position every
                    step: a pin carries no motion, into friction against it or into its first step once released.

1.6 · Data model

                
FabricSettings: every knob, two lifetimes

                
Fabric.Update calls FabricEffect.Apply(Settings) every frame, which checks
                    every value, clamps it and uploads it, so live knobs take effect on
                    the next step. A value that is not a finite number throws, naming the setting, before anything is
                    uploaded, as does a SolverFrequencyHz that is not positive. The sheet fields, the grid,
                    RestLength and SeedRipple, apply only at Rebuild() rebuild: until then the live sheet keeps the ones it was built with,
                    which Fabric.WidthInParticles, HeightInParticles and
                    RestLength report. With AutoRebuild on, Update and
                    Step rebuild by themselves when any of them, or Fabric's own layout, has
                    changed; a rebuild starts over, so that suits editing a setup, not animating one.
                    Rebuild throws for a grid under 2 × 2 or a RestLength that is not finite
                    and positive; it defaults to 0 on purpose. Damping, BendingPlasticRate and
                    both frictions are fractions per 1/120 s, rescaled to the step (slide 4.7); read as
                    coefficients, the two frictions are also the rest hold's static friction (slide 4.8).

            

            

        


        

            

                
1.7 · Data model

                
Resolution independence

                
Mass and drag are set per area, not per particle. Each point carries the mass of its own cell and
                    catches the air over its own cell:

                
ParticleMass = ArealDensity × RestLength²
ProjectedArea =
                    RestLength²
                

                
Refine the same 3 m × 2 m sheet and the totals stay put. Only the particle count, and the cost,
                    change.

1.8 · Data model

                
Iteration budgets

                
Contacts and bending are the costly parts of a round, so they run on only some of the RelaxationIterations
                    rounds. A budget of k is spread evenly: round i solves when ⌊(i+1)k/N⌋ steps past
                    ⌊ik/N⌋.

                
Gotcha: RelaxationIterations = 0 solves no threads (one pass still
                    runs, so the colliders and the pins' reach hold), but ContactIterations = 0 and BendingIterations
                        = 0 mean every round. FabricSettings.EveryRound names that 0, so a
                    call site can say which it means.
                

                
Gold marks the round where contacts are recorded for the next step's friction and rest test: the last
                    one that solves them.

1.9 · Data model

                
Compression slack and thickness

                
A thread fully resists stretching but may shrink down to CompressionSlack × RestLength
                    before it pushes back. That is what lets cloth crumple.

                
It couples to self-collision. Crush two threads in a row and points two apart sit only 2 ×
                    slack × RestLength apart. If that is under the collision thickness, threads and contacts
                    fight forever and a pile never settles:

                
MinimumCompressionSlackForContacts = SelfCollisionThicknessRatio / 2

                
The default, 0.375, is exactly that minimum at the default thickness. It used to be 0.1, below it: a
                    hanging sheet drapes the same, but a pressed pile now settles to 98–100% resting where it reached
                    91–95%.

1.10 · Data model

                
Wind is a velocity, not a force

                
Wind is the air's velocity. Drag acts on the cloth's motion relative to it,
                    scaled by how squarely the panel faces the flow: edge-on catches nothing. That one term is what
                    makes cloth flutter.

                
Divide drag by the particle mass and RestLength² cancels, so the acceleration depends
                    only on the material and the speed. That is why the demo calls 2.5 m/s enough to stream a light
                    sheet out flat.

2.1 · Fabric

                
Two kinds of property

                
Fabric is the CPU model of the sheet. It never draws and never steps on its own; it
                    builds the particle array, uploads it, and forwards Update to the effect.

                
Its layout properties (Origin, Orientation, Rotation, PinMode,
                    PinnedIndices), like the sheet fields in the settings (the grid,
                    RestLength, SeedRipple), are read only inside Rebuild(). The
                    constructor builds nothing: Rebuild() does, or the first Update, Step,
                    Cut or CaptureSurface, so the layout can go in an object initializer. With
                    FabricSettings.AutoRebuild on, Update and Step also rebuild
                    whenever any of those inputs has changed.

                
Rebuild() always starts from whole cloth: it clears every tear and cut
                    stroke and restarts the solver clock. It checks everything first, so a bad setting throws and leaves
                    the live sheet running. Every rebuild, however it came, raises Rebuilt, the place to
                    size a host's buffers; it is raised even if the final Apply fails, since the sheet has
                    been replaced either way.

2.2 · Fabric

                
Placement: origin, plane, attitude

                
    
                    
  • Origin is the middle of the sheet on both axes, so changing resolution or
                        spacing leaves it where you put it.
                    
    • 
                    
  • Orientation picks the plane: Vertical spans X and Y,
                        Horizontal spans X and Z.
                    
    • 
                    
  • Rotation rotates the offset from the origin, so the sheet pivots in place.
                        Rebuild normalizes it, and throws for one of zero length.
                    
    • 
                

                
Rotation is a starting attitude only. Gravity, wind and colliders stay in world space, so only the
                    pins (brass) hold a tilt. Any angle is safe: a rigid rotation keeps every rest length and fold
                    angle, so the first step has nothing to correct.

2.3 · Fabric

                
SeedRipple: a wave that costs no stretch

                
A perfectly flat sheet has no preferred side to buckle to, so the build adds a small wave sin(0.7·w)·cos(0.5·h)
                    out of the plane, sized as a fraction of the spacing: FabricSettings.SeedRipple, 0.05
                    by default and clamped to MaxSeedRipple (0.5). Raise it for a sheet dropped flat.

                
A wave makes every thread longer than the flat gap it spans. Instead of starting stretched, the
                    in-plane spacing shrinks by Pythagoras until the steepest thread is exactly one rest length.
                    Every other thread starts slightly short, and threads only resist shortening past CompressionSlack,
                    so that is free.

                
steepest rise = ripple · 2·sin(k/2)  (k = 0.7 per column)
spacing =
                    √(RestLength² − rise²)

2.4 · Fabric

                
Pins and their anchors

                
At build the pinned set is the union of the PinMode preset and
                    PinnedIndices; on the live sheet SetPinned(index, bool) changes it.
                    Interior points are fine.

                
Every free point then gets its nearest pin and the shortest path to it through the
                    weave, by a multi-source Dijkstra over the surviving threads. Those go up as the solver's own 8-byte
                    anchors (Index, MaxDistance), which it copies into
                    AnchorIndex and MaxAnchorDistance.

                
    
                    
  • Colour = which pin a point hangs from; number = path length in rest lengths.
    • 
                    
  • Diagonals count only while shear threads exist (UseShearingConstraints), or the
                        limit comes out too short and holds the cloth taut.
                    
    • 
                    
  • A piece cut off from every pin gets −1 and falls; a pin gets 0.
    • 
                    
  • A pin change, a cut or a change of UseShearingConstraints marks the anchors stale.
                        FlushAnchors re-measures them once before the next step, on the CPU, with no
                        readback.
                    
    •

2.5 · Fabric

                
Why long-range attachments exist

                
In a Jacobi round each point only sees its neighbours, so a pin's pull travels one point per
                    round. With 10 rounds a step, a long sheet never fully feels its pin, and it sags like rubber
                    under its own weight.

                
But no point can ever be further from its pin than the path through the weave. So after the thread
                    corrections, the solver simply clamps each point onto that sphere around its anchor, in one go. It
                    reads the 8-byte anchor, not the 64-byte record, and is switched off while nothing is pinned.

                
Both chains below run the solver's rules: averaged Jacobi, stiffness 0.9, 10 rounds, 120 Hz. Only the
                    right one clamps.

2.6 · Fabric

                
Folds and who owns them

                
Bending is measured as the dihedral angle across a hinge: the angle between the two triangles
                    that share it. Each grid square is split along one diagonal, giving three folds per point, all owned
                    by the point at the square's lower-left corner. That is why RestAngles is a float3:
                    X across, Y down, Z diagonal.

                
The across and down folds reach into the neighbouring square, so they need a row below or a column to
                    the left. Edge points own fewer folds.

                
The angle is signed: π is flat, one way of closing runs to 0 and the other to 2π, so a crease can't
                    pop through flat and be held on the wrong side.

                
Click a point to make it the owner.

2.7 · Fabric

                
Rest angles and plasticity

                
The build measures every fold of the starting shape and stores it as the rest angle, so the seed wave
                    holds instead of flattening. The C# DihedralAngle must match the shader's exactly, or
                    the sheet twitches on its first frame.

                
Once a step, each point re-measures its folds. A fold bent more than
                    BendingPlasticYieldDegrees away from its rest angle drags the rest angle towards itself
                    at BendingPlasticRate, a fraction per 1/120 s rescaled to the step. Release it and
                    it springs back only to the new rest: a crease.

                
The library default rate is 0: folds always spring back fully, and the demo leaves it
                    there. The slider below starts at 0.05 to show the effect.

3.1 · FabricEffect

                
What FabricEffect owns

                
FabricEffect is the GPU side: it loads the compiled solver and takes its own copy of it
                    (Clone), allocates the sheet's buffers in SetParticles, runs the
                    fixed-step clock and dispatches the passes. Fabric never touches a buffer directly.

                
    
                    
  • Records are the full 64-byte particles, twice, for double buffering.
    • 
                    
  • Position state is a slim float4 copy (xyz; w 0 free, 1 pinned, 2 held),
                        twice. Constraint rounds read eight or more neighbours each, so 16 bytes instead of 64 is most
                        of their bandwidth.
                    
    • 
                    
  • Anchors (8 bytes) and the tear mask (4 bytes) per particle are written only from
                        the CPU; the hold state (4 bytes) and the rest test's running average of the
                        velocity (12 bytes) only by the passes.
                    
    • 
                    
  • Feature buffers follow their switches. Self-collision brings the spatial hash (a
                        power-of-two table, at least one bucket per particle, min 1,024, max 2²³, 32 slots each), the
                        candidate lists (up to 32 partners) and the contact state; bending brings twelve 8-byte fold
                        shares per particle; pressure brings its pyramid. Each is made when its feature is turned on and
                        released when it is turned off, with a one-element placeholder bound meanwhile.

3.4 · FabricEffect

                
Plumbing: uploads, parameters, dispatch limits

                
    
                    
  • Uploads write the front buffers only. Every pass writes all of its output before anything
                        reads it, so the back buffers never show what an upload left there. Scratch arrays are reused,
                        with no LINQ, and SetParticles makes the new buffers before releasing the old.
                    
    • 
                    
  • An upload stalls far longer than a frame. SetParticles, and building the
                        pressure pyramid, set _skipNextFrameTime, so the next Update runs
                        exactly one step instead of trying to catch up on the stall. One rather than none, so normals
                        exist before the first draw. UpdateParticles leaves the clock alone: a host
                        animating its pins uploads every frame.
                    
    • 
                    
  • Each sheet has its own effect. ContentManager.Load hands every caller one
                        shared instance, so the constructor takes a copy with Clone(). Dispose
                        releases the copy with every buffer, and any call after it throws
                        ObjectDisposedException.
                    
    • 
                    
  • Parameters are looked up once and cached, including absent ones: the compiler strips
                        uniforms the shader never reads, and setting one of those becomes a no-op rather than a crash.
                        Passes are looked up once too, in the constructor, since Step dispatches up to ~100
                        times a frame.
                    
    • 
                    
  • There is no unsigned setter, so SetUInt passes the same bits as an
                        int.
                    
    • 
                    
  • A dispatch over 65,535 groups throws. On the GPU it would fail silently, as cloth frozen
                        from some row down.
                    
    • 
                    
  • Time is summed in double: a float adding 1/120 s steps drifts by percents
                        after a few hours.

3.5 · FabricEffect

                
Drawing between steps

                
The solver steps at 120 Hz; the screen may not. Drawn at the latest step, motion jerks: some frames
                    advance two steps, some none. InterpolationFraction draws a blend of the last two poses
                    instead.

                
The trick is a constant lag. The fraction is chosen so the drawn pose is always
                    drawLag behind the wall clock:

                
fraction = 1 − (drawLag − accumulator) / timeStep
⇒ drawn time = wall time − drawLag
                

                
drawLag follows the accumulator's peak over the last 0.5–1 s: it rises at once, sheds at
                    1% of real time, and never exceeds one step. In step with the solver (60 fps) the peak is 0, so it
                    costs nothing.

                
Normals blend by the same fraction. The last round of each step writes the normal of the pose the
                    step ends in, and keeps the one it began in, packed into four bytes, so shading turns as smoothly as
                    the cloth moves.

3.6 · FabricEffect

                
Readbacks and diagnostics

                
Reading GPU memory on the CPU makes the CPU wait until the GPU has finished everything queued before
                    it, then the GPU sits idle while the CPU prepares the next frame. That bubble is the cost, not the
                    bytes copied.

                
    
                    
  • Counters are 64-bit running totals, never reset: a low and a high word, with the carry added by
                        a second atomic only when the low word wraps. The CPU differences two samples. A 32-bit tally of
                        resting particle-steps wrapped in about 34 s on a 1024² sheet.

                        pin count changes, and only then: a host uploading every frame with the same pins keeps its
                        window, which used to restart at every upload and never close.
                    
    • 
                    
  • Each compute group tallies in groupshared memory and adds once per group, not one
                        global atomic per particle.
                    
    • 
                    
  • One fetch per step serves every sampler: ReadCounters caches by TotalStepCount.

4.1 · The kernels

                
Eight kernels, one thread per particle

                
FabricSimulation.fxh holds every compute kernel; FabricCompute.fx only
                    lists them as eight passes. Each is dispatched one-dimensionally in groups of 256 threads, and
                    thread i owns particle i.

                
The rule that shapes everything: gather, never scatter. A thread computes a correction only
                    for its own particle, by reading its neighbours. Nothing writes another particle's position, so
                    there are no atomics on positions and no races. The price is that a shared quantity is evaluated by
                    each of its particles separately. Threads and contacts still are; folds, the costliest, are solved
                    once by their owner in a pass of their own, which writes every particle's share for the round to
                    gather.

4.3 · The kernels

                
The rest deadband

                
Verlet turns every correction into velocity. Constraints that never quite agree leave a little noise
                    each step, Verlet carries it into the next, and settled cloth twitches forever.

                
Below RestSpeedThreshold the carried motion is discarded: not damped, which would
                    slow everything, and not frozen into a pin, which would make frozen points fight their neighbours.
                    (The rest hold, slide 4.8, keeps settled cloth still another way.)

                
But a point gently starting to move is slow too. The drive test spares it: if its velocity points
                    along its acceleration by more than RestDriveFraction of one step's worth, it is being
                    driven, not resting. Points touching a collider or other cloth skip the drive test: friction acts on
                    carried motion, not on the force, so cloth creeping down a sphere would otherwise never come to
                    rest.

                
A slow swing is slow too, and it moves across the force, so the drive test cannot tell it from noise:
                    a sheet settling to a new lean as a gust died hung a metre short for tens of seconds. Noise is as
                    likely one way as the other and averages away; a swing does not. So each particle keeps a running
                    average of its velocity over about 1/15 s, capped at twice the threshold, and motion averaging
                    above a quarter of the threshold is kept, however slow, on a point touching nothing. One that
                    touches something is stopped all the same, as friction stops slow sliding: a pile's compaction creep
                    is exactly that, unless a push past what friction and the hold take is driving it along its support
                    (slide 4.8), when it slides instead.

                
The deadband only works while solver noise stays under the threshold: push the noise past RestSpeedThreshold
                    and the wander comes back.

4.4 · The kernels

                
One round: gather, then average

                
In a Jacobi round every correction a point gathers was computed against the same stale
                    positions. Add up eight thread corrections and the point overshoots up to eightfold, its neighbours
                    do the same, and the sheet shakes itself apart. Averaging keeps each round a safe partial step.

                
The solver averages three groups separately: threads, folds and contacts. Averaged together,
                    twelve soft fold corrections would drown the few strong thread ones, and one contact would average
                    away among eight threads exactly when it matters.

                

                    
                    
                    A taut sheet, pinned all round and stretched 4%, with a few millimetres of noise. One relaxation round every 120 ms, using the solver's thread function.

4.5 · The kernels

                
Twelve folds per particle, each solved once

                
Bending is the Position Based Dynamics dihedral constraint (Müller et al.). Its correction for each
                    of a fold's four particles is the angle's gradient, scaled by the angle error. The gradients blow up
                    as a fold flattens, so they are pre-multiplied by sin θ, and the sign flips past π because the angle
                    is signed.

                
A particle is the hinge of six folds and a far corner of six more, owned by up to six different
                    cells. Each particle solving all twelve itself, as the rounds used to, solved every fold four times
                    over. Now CS_Bend runs before each bending round: each owner solves its three folds
                    once (SolveDihedral, all four corrections at a time), reading the six positions they
                    share once rather than twelve, and writes them as twelve half-precision shares. The round gathers
                    the particle's twelve through BendingStencil's (owner offset, kind, role) entries.
                    Click a particle.

                
Fold solves per round fall from 12 to 3 per particle. Compiled with d3dcompiler_47
                    at cs_5_0, the constraint kernel went from about 2,135 instruction slots to about 680,
                    and is about 673 now, some 150 of them the end-of-step normal that only the last round runs; CS_Bend
                    is about 486, dispatched only on bending rounds. Those are instruction counts. Timed since on a GPU,
                    the latest round of kernel changes, these six reads among them, ran equal at 96 × 64 and 15–20%
                    faster per step at 192 × 128 and 384 × 256.

4.6 · The kernels

                
Self-collision through a spatial hash

                
    
                    
  • Space is cut into cubes 1.5 thicknesses wide, the candidate radius, so anything within
                        that radius of a point lies in the 27 cubes around it.
                    
    • 
                    
  • Cubes are hashed (Teschner et al. primes) into a fixed power-of-two table: no world bounds, no
                        resizing. Unrelated cubes may share a bucket; the gather re-checks each entry's own cube, so an
                        aliased bucket costs a rejected test and never lists anyone twice.
                    
    • 
                    
  • Each bucket holds 32 entries. An overflowing particle is dropped for that step and counted, so
                        SampleSpatialHashOverflow can report contacts never seen. It held 16, but a crushed
                        pile wants 29–40: its contact set then changed from step to step, which kept it from ever coming
                        to rest.
                    
    • 
                    
  • Once a step, CS_GatherCandidates keeps each free or held particle's partners within
                        the candidate radius, up to 32. It skips the cells its radius cannot reach, about a quarter of
                        the 27, and every contact round then tests only that list, instead of searching again. A full
                        list is counted too.
                    
    • 
                    
  • The lists are laid out by rank: a count per particle, then every particle's first partner, then
                        every second, so a wave reading its particles' k-th partners reads consecutive words.
                    
    • 
                    
  • The 8 weave neighbours are skipped, since threads handle them, unless the thread between them is
                        torn: then they are two lips of a tear and must collide. The test is an index offset and one
                        mask word, with no division.
                    
    • 
                

                
This 2D version uses 9 cells instead of 27, and a thickness of two thirds of a cell. Click a point to
                    gather its candidates.

4.7 · The kernels

                
Colliders, friction and the step rate

                
Colliders are projected every round: a point inside the sphere or under the floor is moved to
                    the surface. Projection is idempotent, so repeating it is safe. Friction runs once a step, in
                    CS_Integrate, by removing a fraction of the tangential carried motion; applied per
                    round it would compound and fight the solver. Self-friction uses the previous step's recorded
                    contacts and removes sliding relative to the partner, so a heap moving as one piece is not
                    braked.

                
The same pass reports what carries the point, for the rest hold's static friction (slide 4.8):
                    the summed normals of the sphere or floor where they face against gravity, and of the cloth it rests
                    on, counted per partner by the recording round; pinched between layers, straight against gravity.
                    With it comes the strongest of their static grips: the friction settings themselves, not the
                    per-step rates the sliding friction above uses.

                    are stated per 1/120 s, and Apply rescales them to the step, so the same numbers
                    mean the same at any SolverFrequencyHz. The carried motion is rescaled too, and with it
                    the partner motion friction compares against, so even a live change of rate changes cost and
                    stability, not how the cloth moves.

4.8 · The kernels

                
Holding settled cloth still

                
The deadband discards carried motion, but a resting point still gets gravity's push every step, 0.68 mm
                    at 120 Hz, and an approximate push back from what it rests on. The residuals creep. A sheet
                    dropped on the floor twitched at about 170 µm a step, with single-step pops of 100–460 mm,
                    and its heap spread flat over a minute.

                
UseRestHold adds what friction adds. A point that has rested for
                    RestHoldDelay (0.05 s, and never under two steps, so a bounce's apex never counts)
                    and is supported, touching the floor, a collider or other cloth, or joined by a whole thread
                    to a held point, is held. It still runs every round with every force, except that a push it
                    can ignore is not applied to it. At the end of the step a net move within its wake was noise,
                    or a pull it can ignore, and snaps back to where the step began; a larger pull, by a thread or a
                    contact, frees it, and so does a larger push that actually moved it: braced by its neighbours, it
                    stays held.

                
    
                    
  • Wake distance = RestHoldWakeFraction × RestSpeedThreshold / 120 Hz
                        = 0.5 × 0.06 m/s / 120 Hz = 0.25 mm, the same at any rate. The push the hold
                        ignores is the same fraction of RestSpeedThreshold per 1/120 s: 3.6 m/s²,
                        at any rate. A point hanging on held cloth, whose only push is gravity braced by its threads,
                        takes that push limit as its wake instead, never under an eighth of the wake distance.
                    
    • 
                    
  • Neighbours treat a held point like any other, never as a pin: full corrections against a frozen
                        point overshoot, and wake the pile.
                    
    • 
                    
  • A resting point that something carries gets no push into its carrier, which would only project
                        it back, approximately, while the pile sank into itself. Of the rest, static friction holds what
                        lies within its cone; what is left past the limit drives the point, which slides under the
                        kinetic friction rather than creeping by one push a step.
                    
    • 
                    
  • A hanging sheet touches nothing and is never held, so it swings and settles exactly as before.
                    
    • 
                

                
Static friction reads the carrier's friction setting as a coefficient, μ = f / (1 − f): 0 holds
                    nothing, 1 anything, and 0.35 holds about 28°. It reads the setting itself, uploaded beside the
                    per-step rate the sliding friction uses, because a cone is an angle and must not change with the
                    step; it used to read the per-step rate, which held 13.5° at 240 Hz and 54° at 60 Hz. The
                    step rate below changes the push per step, not the cone, the limit or the wake.

                
Measured on the 96 × 64 sheet dropped on the floor: 99.7–99.9% of the pile bitwise still, with no
                    drift; a pressed sheet, a sphere pushed through the pile and gravity turned sideways all re-freeze,

4.9 · The kernels

                
Aerodynamic pressure as added mass

                
Per-particle drag treats every point as alone in the air, so a falling sheet stays flat. Real air
                    under the middle of a sheet has further to escape than air at the rim, so the middle is held back
                    more and the sheet domes, like a parachute.

                
The solver models that as added mass: air dragged along with the cloth. Broad motions drag
                    more air than fine wrinkles. So each particle's normal acceleration is split into bands with a
                    pyramid (each level averages 2×2 cells of the one below, inside zero padding), and each band is
                    divided by its own effective mass:

                
response(level) = ρcloth / (ρcloth + AddedMassScale · 2level
                    · √2)
                

                
Dividing can only shrink a term, so the model cannot blow up however heavy the air. Near the rim,
                    coarse cells average in the still-air padding, so the rim keeps more of its acceleration than the
                    middle. This 1D slice through a falling sheet shows it.

                
The pyramid is fed the push each particle actually got. It used to be fed the raw acceleration,
                    gravity included, even where the rest hold had taken gravity's push away, so the air refunded a push
                    never applied: a pile under pressure hovered, 86% held after 20 s, where it is 99% now. CS_ApplyPressure
                    corrects the positions only; the records keep CS_Integrate's for the rounds to read.
                

                
That needs padding. The base is the next power of two at least twice the sheet's longer side, where
                    that fits in 4,096, so every edge keeps a wide margin of still air. It used to be the smallest
                    square that held the sheet: a 64-wide sheet filled it, the coarse levels saw no rim, and it never
                    domed. Try 64 points with the old base.

5.1 · Tearing & cutting

                
One owner per thread

                
The weave is implicit in the grid, so damage is a set of flags. Each particle carries one
                    uint of FabricTearFlags, and every thread has exactly one owner, so
                    both of its ends agree whether it is torn. A point owns the threads to its right and above it, and
                    both diagonals of the square to its upper right.

                
Three more bits mark dead folds: a fold whose two triangles lost any of their five threads.
                    The CPU precomputes them after every cut, so bending checks one bit instead of five.

                
The GPU never sees the ownership. FabricEffect.BuildTearMask expands the flags on the
                    CPU into one word per particle: its eight links, torn or not, in bits 0–7, and the dead bits of the
                    three folds it owns in bits 8–10. A pass reads that one word instead of up to nine.

5.2 · Tearing & cutting

                
A stroke severs threads

                
Cut(start, end) takes metres on the flat sheet, because damage belongs to the
                    weave, not to wherever the cloth hangs now. It checks every point first, converts to grid units in
                    double precision and clips each segment (Liang–Barsky) to two cells past the sheet. Then it visits
                    only the squares along the segment, row by row: a thread is severed when the stroke properly crosses
                    it. That finds exactly the threads the old bounding-box scan found, as a test checks against brute
                    force, at the cost of the segment's length rather than its box's area.

                
    
                    
  • The endpoints are ordered first, so a stroke drawn either way severs the same threads.
    • 
                    
  • A point exactly on the stroke's line counts as left of it. A stroke running exactly along a row
                        of points therefore severs the threads on one side, deterministically, and never a thread
                        lying on the line itself.
                    
    • 
                    
  • Whole cloth severs into a scratch array, made once and kept, so a miss allocates nothing after
                        the first; the first hit adopts it as the tear state.
                    
    • 
                    
  • Severing, recording and applying sit in a finally, so a throw part way can never
                        leave the GPU mask, the dead folds or TriangleCount stale.
                    
    • 
                

                
Drag the two handles. 5.4 · Tearing & cutting

                
Clean lips: the cut mesh

                
The simulation can only sever whole threads, so a hole drawn from the plain list is a staircase.
                    CreateCutMesh() keeps the whole triangles and replaces each damaged one with the faces
                    of its cut graph: every stroke near it, with any number of joints, crossings, T-junctions and
                    overlapping re-cuts, split into pieces that are then ear-clipped. This is flat 2D geometry,
                    computed once per change of damage, never per frame: the same instance comes back until the next
                    cut, tear, mend or Rebuild, so treat it as read-only.

                
A piece's corner that lies on the lip is not a particle. It becomes a seam vertex: a weighted
                    blend of three nearby particles on its own side of the cut (its carriers), chosen so none is reached
                    across the stroke and all hang together through the surviving weave. As the rip opens, each lip
                    rides its own cloth. On a strip one particle wide, where no three span any area, two carriers along
                    it and an offset across it, along the cloth's normal, keep its full width.

5.6 · Tearing & cutting

                
Cutting what the player sees

                
Crumpled cloth no longer lies where it was built, so a knife cuts against the sheet itself. CaptureSurface
                    reads the pose back once, at the press. A FabricStroke over it records each ray's nearest
                    layer, or its miss, as the drag goes, and the preview is drawn from those hits. On release, Cut(stroke)
                    joins the samples in flat-sheet coordinates without picking again; Cut(rays) does the
                    same from a list.

                
When the knife slides off one layer onto another, two hits can be close in space but far apart across
                    the cloth. Joining them would cut a straight line through cloth the knife never touched, so the
                    stroke breaks when

                
distance across the cloth > distance through space + 2 · RestLength

                
A miss is different. Across one, two samples join only if the flat path between them crosses a
                    recorded cut or a torn thread: the knife passed over an open rip. A run that ends or starts at a
                    miss reaches on to a recorded cut, or half a cell past the sheet's edge, when that lies within its
                    last sample spacing plus a cell, so no threads are left holding the piece on.

6.1 · Picking

                
Which point of the weave is under the cursor?

                
Once cloth has crumpled, only its current triangles can answer that. CaptureSurface()
                    reads the sheet back once and picks against the cut mesh, seam vertices included: the very
                    one CreateCutMesh returns, cached until the damage changes, so what can be picked is
                    exactly what is drawn. FabricSurface.Raycast then answers any number of rays against
                    that pose, for the whole gesture.

                
    
                    
  • A box test first, so a ray nowhere near the cloth costs one check, the common case while
                        previewing.
                    
    • 
                    
  • Then a uniform grid, walked cell by cell along the ray (a 3D DDA, in double precision), testing
                        only the triangles filed in the cells the ray crosses. Under 64 triangles it tests them one by
                        one.
                    
    • 
                    
  • Each test is two-sided Möller–Trumbore, because a crumpled sheet shows back faces everywhere:
                        floats to reject, doubles to decide, so a ray down a shared edge reports its layer once.
                    
    • 
                    
  • Hits are insertion-sorted nearest first into a span the caller provides: no allocation per
                        ray.
                    
    • 
                    
  • The answer the host cannot compute itself: the hit's barycentric weights blend the three
                        corners' flat-sheet coordinates into a flat-sheet point, ready for Cut.
                    
    • 
                

                
On a 512² sheet, 520,000 triangles, a nearest-layer ray takes about 1–8 µs, against 3.4–6.5 ms
                    before; filing the grid takes about 35 ms per capture. Move over the crumpled patch on the

6.2 · Diagnostics

                
Two measurements a screenshot can't give you

                
Both take the array from one ReadBack(), re-derive everything from positions, and
                    allocate freely: they are for debugging, not frame work. Pass CopyTearState() on a torn
                    sheet so a rip's lips count as touching cloth, and dead folds are skipped. Both check that the grid
                    and the tear state fit the array, and throw if not.

                
PenetrationCheck counts pairs of non-neighbouring points closer than the cloth is thick, and
                    separately those overlapping by more than a quarter of it: one layer through another. It
                    deliberately builds its own exact hash with unbounded buckets. A check that read the solver's
                    buckets would miss exactly the pairs the solver missed when a bucket overflowed. Give it the
                    thickness the solver runs with, SelfCollisionThicknessRatio (at least 0.05) × Fabric.RestLength,
                    the spacing as built; a thickness that is not a positive number counts nothing.

                
CreaseCheck compares each fold's current angle with its rest angle. That separates cloth
                    folded because something presses on it (rest flat) from cloth folded because it has creased (rest
                    bent).

6.6 · Wrap-up

                
What changed

                
Every finding in the tour, in order of importance, as the code now stands at 1.0.0. The C# builds, 81
                    unit tests pass and every HLSL kernel compiles with Microsoft's d3dcompiler_47 at
                    cs_5_0. The kernel figures in item 12 are instruction counts; the rest hold and the
                    passes after it were measured on a GPU, stepping the real library. Chapters in brackets.

            

            

                
1 · Fixed
                    
Two sheets from one ContentManager shared one solver Effect [3]

                        
Each FabricEffect clones the loaded effect and disposes its copy. A missing
                            technique or pass throws naming it, and Dispose ends the instance.

                

                
2 · Fixed
                    
One non-finite setting poisoned the sheet [1, 3]

                        
Apply checks every setting before uploading any and names the bad one; SolverFrequencyHz
                            must be positive; AirDensity and DragCoefficient clamp at 0. A NaN
                            frame time counts as none.

                

                
3 · Fixed
                    
Rates and carried motion depended on SolverFrequencyHz [4]

                        
Damping, both frictions and BendingPlasticRate are per 1/120 s,
                            rescaled per step, and DisplacementScale rescales the carried motion, so even a
                            live change keeps how the cloth moves.

                

                
4 · Fixed
                    
The grid and RestLength were half-live, and Rebuild cleared state
                        before checking [1, 2]

                        
Both are captured at Rebuild, which checks everything before touching the live
                            sheet; SetParticles makes the new buffers before releasing the old; the
                            constructor builds nothing.

                

                
5 · Fixed
                    
No live API for pins, and moved pins kicked and rubbed [2, 4]

                        
SetPinned and IsPinned. Anchors live in their own 8-byte buffer,
                            re-measured on the CPU once before the next step with no readback, and a pin carries no
                            motion.

                

                
6 · Fixed
                    
Cutting: half-applied throws, bridging slow drags, rays that could not cross or reach a
                        cut, unclipped strokes, no surface check [5]

                        
Points checked first, the rest in a finally; every segment of a cut recorded,
                            collinear ones merged; FabricStroke and AssembleRayStroke;
                            Liang–Barsky clipping in double; surfaces stamped with their owner and build.

                

                
7 · Fixed
                    
The cut mesh: a three-stroke seam limit, cracks through lattice points, vanishing one-cell
                        strips [5]

                        
Rewritten as a cut graph per damaged triangle, ear-clipped, with rim points worked out once
                            per thread, region signatures over every (stroke, side) pair, and two-carrier seam vertices.
                            Fuzzed over 26,000 random sheets with no bridging, cracks, winding or weight errors; the
                            only holes left are scraps of fewer than two particles.

                

                
8 · Fixed
                    
Solver edge cases [3, 4]

                        
RelaxationIterations = 0 keeps the colliders and the pins' reach; contact state
                            no longer goes stale; a failed pyramid build no longer half-applies Apply, and
                            the pyramid is released when pressure is off; a still-air margin, so 64² sheets dome; needle
                            tests with ≤, so no NaN; no fixed −Z normal; coincident contacts parted by
                            history before index.

                

                
9 · Fixed
                    
Diagnostic totals wrapped [3]

                        
64-bit totals with a carry, in 15 counter slots, so the resting fraction no longer wraps in
                            34 s on a 1024² sheet; full candidate lists are reported with the hash's overflow.

                

                
10 · Fixed
                    
Packaging and docs [1, 2, 3, 5, 6]

                        
Targets under buildTransitive/, with build/ importing them; the
                            shader copy on by default only for an executable; BorrowedTorchFabricContentDir
                            with or without a trailing slash. README: scissors as one polyline per layer, the
                            buffer-swap reasoning, RestLength 0.03–0.06, a stale fps figure gone. FabricSettings.EveryRound,
                            and FabricPinMode docs saying Top is the last row.

                

                
11 · Done
                    
A tests project

                        
Tests/: 81 xUnit tests over the cut mesh, picking, severing, clipping, ray
                            strokes, anchors, the tear mask and settings, through InternalsVisibleTo, in
                            the solution and outside the library's globs. The demo uses FabricStroke, the
                            grid as built, and P to release and re-pin its top edge.

                

                
12 · Done
                    
Lighter kernels, by instruction count [4, 5]

                        
CS_Bend solves each fold once: fold solves per round fall from 12 to 3 per
                            particle, and the constraint kernel from about 2,135 instruction slots to about 680, some
                            150 of them the end-of-step normal that only the last round runs, with CS_Bend
                            at about 493 on bending rounds only (673 and 486 today). Contact partners are gathered once
                            a step, up to 32, rather than searched for in 27 buckets every contact round. A pass reads
                            one tear-mask word instead of up to nine. Feature buffers exist only while their feature is
                            on.

                

                
13 · Done
                    
Faster on the CPU, measured [5, 6]

                        
Picking: about 1–8 µs per nearest-layer ray on a 512² sheet (520,000 triangles), against
                            3.4–6.5 ms before; the grid files in about 35 ms. The cut mesh: 256 × 256 with 300 strokes
                            in 353 ms instead of 826 ms. Severing scans only the cells along a segment, and uploads
                            write the front buffers only, with no LINQ.

                

                
14 · Done
                    
Normals blend between steps [1, 3]

                        
The last constraint round computes the normal of the pose the step ends in, and keeps the one
                            it began in, octahedron-packed into four bytes: the record grows from 60 to 64 bytes. FabricEvaluateVertex
                            and the new FabricInterpolatedNormal blend them by the fraction, so shading
                            turns as smoothly as the cloth moves, and the drawn normal no longer trails the drawn
                            position by a step.

                

                
15 · Fixed
                    
Piles never came to rest [4]

                        
UseRestHold: a supported point that has rested for 0.05 s is held, and a
                            net step move within 0.25 mm snaps back; buckets and candidate lists hold 32. A dropped
                            pile went from 170 µm a step and 100–460 mm pops to 99.7–99.9% bitwise still, at a
                            cost within noise. SampleHeldFraction reports it.

                

                
16 · Fixed
                    
The deadband froze a slow swing; resting cloth ignored wind and slopes, and hovered under
                        pressure [4]

                        
A running average keeps slow motion that persists on cloth touching nothing (7 cm short
                            of the truth, not a metre); a carried resting point loses only its push into the support,
                            and static friction holds the rest within its cone; the pressure pyramid is fed the push
                            actually applied (86% held after 20 s, now 99%).

                

                
17 · Fixed
                    
Stale sampling windows and rebuild edges [2, 3, 6]

                        
The resting and held windows restart only when the pin count changes, so a host uploading
                            every frame sees them move; Rebuilt is raised even when Apply
                            fails; SyncPins tells a sheet of another shape apart; AutoRebuild
                            compares the clamped SeedRipple; the diagnostics check their inputs; the anchor
                            test that could not fail now can.

                

                
18 · Done
                    
Faster passes, timed on a GPU [4, 5]

                        
Six position reads in CS_Bend instead of twelve, weave neighbours read once a
                            pass, positions-only ApplyPressure, candidate lists by rank, cells beyond the
                            radius skipped: equal at 96 × 64, 15–20% faster per step at 192 × 128 and 384 × 256. On the
                            CPU, cut meshes and triangle lists are kept until the damage changes.

                

                
19 · Done
                    
The settings hold every sheet field, and can rebuild by themselves [1, 2]

                        
SeedRipple in FabricSettings, AutoRebuild and Fabric.Rebuilt,
                            TimeStep as the solver takes it, and CompressionSlack 0.375, the
                            least that does not fight self-collision.

                

                
20 · Fixed
                    
The static-friction cone followed the step rate [4]

                        
It read the per-step friction, so 0.35 held about 28° at 120 Hz but 54° at 60 Hz
                            and 13.5° at 240 Hz. The settings themselves now go up as the static grips: the same
                            cone at any rate, and the same results at 120 Hz to within rounding. The contract
                            version stays 3: 1.0.0 is not out yet, so no header in the wild lacks the new inputs.

                    

                

                
21 · Fixed
                    
The rest rules' push thresholds followed the step rate [4]

                        
What a resting point ignored, and what a touching point crept under instead of sliding, went
                            as 1 / dt. Pushes are now judged as accelerations (3.6 m/s² at the defaults) and pulls
                            as distances (0.25 mm), a held point loses its hold only to a push that moves it, and a
                            driven touching point slides. A 50° slope slides at every rate, the ball sheet slides off in
                            5.0–5.5 s from 60 to 240 Hz, the piles hold as before at 120 and 240 Hz, the
                            swing is bit-identical and the cost within a few percent; past about 300 Hz the
                            solver's own residual takes over and the hold errs toward holding.

                

                
Not changed, and why

                
Kept
                    
The 1D row-major dispatch order [4]

                        
2D tiles might reuse caches better on wide sheets, but whether the constraint pass is
                            memory-bound needs profiling on a GPU first.

                

                
Kept
                    
A full cut-mesh rebuild per change of damage [5]

                        
It is 2.3 times faster now. An incremental cache would tie correctness to every walk limit in
                            the builder.

                

                
Overall
                    
A carefully engineered solver

                        
The architecture is unchanged and still clean (CPU model, GPU effect, host-owned rendering),
                            the numerics are defensive in the right places, and the failure modes are measured rather
                            than guessed. The issues were edges, not foundations. It has run on a GPU since: the rest
                            hold, the latest kernel pass and the rate-independent friction cone were all measured there,
                            and the rest rules were then rebuilt, on the same piles, so the step rate has no hand in
                            what resting cloth ignores.
